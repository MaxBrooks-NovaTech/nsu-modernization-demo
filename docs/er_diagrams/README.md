# ER Diagrams

Two SVGs, generated directly from the real schema definitions (not hand-drawn or approximated):

- **`transactional-data-model.svg`** — the 11-table `raw` schema (PostgreSQL), with every real primary key, foreign key, and unique constraint from `db/init/01_schema.sql`.
- **`analytics-data-model.svg`** — the 3 certified marts (`analytics.FactEnrollment`, `analytics.fact_recruitment_funnel`, `analytics.fact_census_enrollment`) from `models/marts/*.sql`, each with its grain, columns, and the certified metrics it feeds from `semantic/metric_definitions.yml`.

## Why the analytics diagram has no FK lines between tables

The three marts are independently materialized, denormalized fact tables — dbt doesn't declare or enforce foreign keys between models the way PostgreSQL does within `raw`. They share **conformed business keys** (`student_id`, `term_id`, `school_id`, `program_id`), shown as dashed lines, which is a real but different kind of relationship than a database-enforced FK — showing them as solid FK lines would overstate what actually exists.

## Regenerating these

Both are generated by small Python scripts (not checked into the repo, since they're one-off generators, not part of the running project) that read the same table/column/key definitions documented in `db/init/01_schema.sql`, `models/marts/*.sql`, and `docs/data-dictionary.md`. If the schema changes, regenerate by hand from those sources rather than trusting a stale diagram.
